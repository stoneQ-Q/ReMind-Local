# ReMind 腾讯 COS 异地加密数据库备份

> 建立日期：2026-07-30  
> 当前状态：新加坡异地备份已启用，真实恢复演练通过  
> 适用环境：腾讯云香港私密测试服务器

## 一、实际资源

- 备份桶：`remind-db-backup-sg-1385855631`；
- 地域：新加坡 `ap-singapore`，与香港业务服务器分离；
- 存储：标准存储、单 AZ、私有读写；
- 版本控制：开启；
- 服务端加密：SSE-COS；
- CDN、全球加速、静态网站和日志存储：关闭；
- 生命周期：
  - 当前版本在修改 30 天后删除；
  - 历史版本在修改 7 天后删除；
  - 未完成分块上传在创建 7 天后删除。

控制台不允许在覆盖整个桶的当前版本删除规则之外，再为相同范围启用“清理无历史版本的删除标记”。删除标记本身不包含备份正文，因此私密测试阶段接受这一限制。

## 二、权限隔离

备份使用独立 CAM 子用户 `remind-backup-runtime`，只关联策略 `ReMindEncryptedBackupWriteReadNoDelete`。

该策略仅允许访问备份桶的 `postgres/*`：

- `PutObject`：写入新备份；
- `HeadObject`：核对对象大小、加密状态和 SHA-256；
- `GetObject`：下载并执行恢复演练。

该账号没有删除、列桶、修改桶、修改生命周期、读取用户媒体或访问其他腾讯云产品的权限。服务器已实际请求删除一个备份对象，腾讯云按预期返回拒绝。

## 三、双层加密

数据库备份在离开服务器前先进行客户端加密：

1. `pg_dump` 生成 PostgreSQL custom-format 备份；
2. 为每个备份生成独立的 96 位随机 IV；
3. 使用 AES-256-GCM 流式加密；
4. 文件头和 IV 作为附加认证数据；
5. 文件尾保存 128 位 GCM 认证标签；
6. 密文上传时再次启用 COS SSE-COS AES-256；
7. 上传后通过 `HeadObject` 核对大小、密文 SHA-256 和 SSE-COS 状态。

任何密文、文件头、IV 或认证标签被修改，解密都会失败。远端对象不包含明文数据库。

备份加密密钥只保存在：

- 服务器 `/opt/remind/shared/remind.env`，权限 `0600`；
- 当前 Mac 的系统钥匙串，服务名称 `app.remind.notes.offsite-backup`。

密钥不得写入 Git、普通文档、聊天、日志或 App。服务器和 Mac 同时丢失且没有额外密钥副本时，远端备份将无法解密；私密测试前应再把恢复密钥保存到可信密码管理器。

## 四、自动运行

- 备份容器每天运行一次；
- 本机明文 custom-format 备份保留 7 天，目录权限 `0700`，文件权限 `0600`；
- 每个本机备份都会生成临时密文并上传到 `postgres/`；
- 上传成功后临时密文从容器临时目录删除；
- 远端当前版本由 COS 生命周期保留 30 天；
- 备份账号没有删除权限，服务器不能主动清理或抹除远端备份。

对象名只包含 UTC 时间，例如：

```text
postgres/remind-20260730T084635Z.dump.enc
```

## 五、实际恢复演练

2026-07-30 已完成以下真实链路：

1. 从生产测试数据库生成 custom-format 备份；
2. 在香港服务器使用 AES-256-GCM 加密；
3. 上传到新加坡私有 COS；
4. 从 COS 下载密文；
5. 校验 COS SSE-COS、对象大小和密文 SHA-256；
6. 使用客户端密钥完成 GCM 解密和认证；
7. 核对解密文件与原始备份 SHA-256；
8. 创建临时 PostgreSQL 数据库并执行 `pg_restore`；
9. 核对恢复结果为 23 张表、12 个迁移；
10. 删除临时恢复数据库和服务器临时文件。

演练完成后：

- 自动备份容器正常运行，重启次数为 0；
- API、Worker 和 PostgreSQL 保持正常；
- 用户、文件和上传记录仍为 0；
- 临时恢复数据库数量为 0；
- 媒体供应商仍为 `disabled`。

## 六、灾难恢复顺序

1. 准备 PostgreSQL 17 和 ReMind 对应发布版本；
2. 从 Mac 系统钥匙串或可信密码管理器取回备份加密密钥；
3. 使用只读恢复凭据下载指定 `postgres/*.dump.enc`；
4. 校验 COS 元数据、对象大小和密文 SHA-256；
5. 使用 ReMind 恢复工具解密并验证 GCM 认证标签；
6. 先恢复到临时数据库并核对表数、迁移数和关键数据；
7. 验证通过后再安排正式数据库切换；
8. 不覆盖或删除原数据库、对象存储桶和已有备份。
